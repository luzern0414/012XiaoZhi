# 硬件语音控制验收

## 已验证

- 本地服务默认待机；只有完整说出“打开语音助手”才允许对话。
- “关闭语音助手”会取消当前输出和控制任务；关闭后普通问题与设备命令均不再调用模型或设备工具。
- 关闭后重新开启不会恢复旧一轮回答，延迟到达的设备回执也不会重新播报。
- 模拟硬件 WebSocket 通过真实后台完成了音量查询、设置、静音/恢复、网络状态、设备信息、重启确认/取消和缺失配网接口提示；Opus 音频入口的开启、音量查询、关闭也已通过本地 SenseVoiceSmall 识别。
- 项目回归测试：91 passed。单会话 OTA、模型回答和 TTS 解码通过；网页服务未启动。
- 设备 MQTT 当前在线：`192.168.16.22`，订阅 `xiaozhi/90_e5_b1_d6_40_5c`。真实设备最近一次只读状态为音量 70%、亮度 75%、WiFi 信号强。

## 现场边界

- 用户现场验证音量查询成功；日志显示识别“当前音量是多少”，设备 MCP 读回 70%，后台播报“当前音量是 70%”。
- 现场“小声一点”“调低音量”曾因命令缺项进入模型；已补齐，真实 Opus / ASR / 模拟设备读写回归通过，分别将模拟音量从 50 调到 40、从 40 调到 30。
- 控制反馈原先遗漏 `tts/start`，固件可能保留聆听状态；已修复为先开始播报、发送完整 `sentence_start` 文字，再排入语音。纯文字待机反馈只更新句子，不制造播报状态。实体屏幕目前仍待新版现场复验，不能据发送日志断言已显示。
- 聆听表示设备采集用户音频；说话表示设备播放助手音频。当前上游在发起模型等待时也会先进入说话状态，因此该标签不精确代表声音已经播放。
- 服务器支持 `listen/stop` 结束采集并提交缓存录音。上游触摸 ToggleChatState 的聆听分支是关闭连接，不是提交；厂家 2.0.3.3 的触摸控制流尚未确认，不能把另一个 EchoEar 分支当作实机证据。若实机点击断连，则须有匹配厂家源码的设备端改动，不能仅靠服务端修改成点击提交。
- 已取得实体设备截图 `data/hardware/screen-latest.jpg`：360×360，顶部“聆听中”，中央表情，下面完整显示待机提示。证明实体可以显示标准句子；尚不能据此确认所有回答的结果文字已通过现场验收。
- 新增硬件连接文字补绘：缓存一轮完整回答，在真正的 `tts/stop` 后短延迟重新发文字，不重启音频、不扣住 stop；检查当前句子和开启代数，防止关闭后旧文本复活。设备控制以完整结果为准，普通回答拼接所有 TTS 分段。
- 14:35:07 的真实模型错误为服务器过载，不是 WiFi 断网。随后直接调用同一 `gpt-6-luna` 接口返回 HTTP 200、7.8 秒；真实后台的 OTA/模型/TTS 文本链路也再次通过。
- 同次“调低音量”被识别为“低音量”；已纳入确定性减音量指令。模型输出前的临时过载支持一次额外重试，输出开始后不重试，鉴权错误不重试，关闭会话后不重试。
- 实机在 14:34:39 进入聆听、14:34:41 断连，没有 `listen/stop`；14:35:14 进入聆听、14:35:15 再次断连。结合现场点击测试，当前触摸行为仍不满足点击结束并回答。未刷写来源不匹配的固件。

- 上述控制协议测试使用本地模拟设备，实体麦克风、扬声器和屏幕仍需现场说话确认；模拟通过不等于实体显示验收。
- 厂家固件未公布断电关机、语音开机、语音配网或关闭原厂本地唤醒检测接口。服务端关闭只控制联网助手，不切断硬件电源，也不能阻止厂家本地唤醒音和屏幕亮起。
- 音量状态文件是最近一次真实 MCP 读回的脱敏摘要；设备断开时不能把它当作实时在线证明。

## 启停

双击根目录 `启动小智.cmd` 启动后台和 IoT，默认不启动网页；双击 `停止小智.cmd` 停止服务。服务重启后助手重新进入待机。
