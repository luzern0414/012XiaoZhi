# 服务部署调研与实际选型

日期：2026-10-19。目标为 Windows 本地开发、接管现有 ESP32 的对话服务，使用用户指定的 gpt-6-luna。

## 复用边界

采用官方固件协议与社区 Python 服务端。现有硬件已有厂商固件，先保留其采集、播放与唤醒功能。本机复用社区服务端的 OTA、WebSocket、VAD、ASR、LLM、TTS 和 Opus 传输，通过配置与根目录适配器运行。独立 Python 服务可完成语音链路，不要求同时部署 Java/Vue/MySQL/Redis 智控台。

来源：

- [官方固件 78/xiaozhi-esp32](https://github.com/78/xiaozhi-esp32)：固件、设备协议和接入文档。
- [社区服务端 xinnan-tech/xiaozhi-esp32-server](https://github.com/xinnan-tech/xiaozhi-esp32-server)：独立运行模式、提供器及部署说明。
- [上游 Deployment.md](https://github.com/xinnan-tech/xiaozhi-esp32-server/blob/eb9dc8ca0fc8a30bc8afb0f302dcfc1578f76a7b/docs/Deployment.md)：Python 3.10、原生 FFmpeg/Opus 与单独下载模型的要求。
- [Windows 部署讨论 Issue #2](https://github.com/xinnan-tech/xiaozhi-esp32-server/issues/2)：仅安装 Python Opus 封装不足，还需要可加载的原生库。

仓库版本、完整性与来源以 `upstream-lock.json` 为准；检索结果以当前检出的实际代码再次核实。

## 安装中解决的问题

1. Python 自动环境下载不稳定：使用 Python 官方 Windows 安装包，校验 SHA-256 和 Python Software Foundation 的有效数字签名，安装到项目内。
2. PyTorch 官方文件源持续慢速传输：使用阿里云 PyPI 镜像分段下载相同 wheel，SHA-256 与官方 PyPI 公布值一致。
3. 原生 Opus：从 conda-forge 的固定 libopus 包提取 DLL，先验证包 SHA-256，再验证最终 DLL 哈希；不要求安装整个 Conda。
4. 模型不在 Git 中：单独下载 936,291,369 字节的 model.pt，SHA-256 与 ModelScope 链接元数据一致。
5. 后台服务标准输入：根目录入口调用原始 app.main，并替换交互式 stdin 监听和 Windows 停止等待，避免后台 EOF 问题。
6. 多网卡：明确广告 WLAN 地址；不能照抄上游自动选择的 SD-WAN 地址。
7. 网页初始化等待麦克风：在生成的网页副本中延后申请录音权限至用户录音操作，添加版本化脚本 URL，避免旧缓存让修改失效。上游工作树保持干净。

二进制来源：[Python 官方](https://www.python.org/ftp/python/3.10.11/)、[conda-forge libopus 元数据](https://api.anaconda.org/package/conda-forge/libopus)、[imageio-ffmpeg](https://pypi.org/project/imageio-ffmpeg/)、[FFprobe Windows 包](https://www.npmjs.com/package/@ffprobe-installer/win32-x64)、[PyTorch 官方 wheel 元数据](https://pypi.org/pypi/torch/2.2.2/json)。版本和精确哈希保存在根目录 `config/runtime-assets.lock.json`。

检索原始结果保存在忽略入 Git 的 `.firecrawl/`，包括部署、音频兼容性和 FunASR 安装检索。最终结论以安装日志和实际端到端验收为准。
