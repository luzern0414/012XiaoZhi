# 硬件语音控制设计与实施步骤

用户已确认只保留硬件交互，并要求语音助手开关可控、避免突然启动。

## 行为约定

- 默认待机；每次新连接和服务重启都从待机开始，不恢复到开启状态。
- 完整说出“打开语音助手”才启用对话；“关闭语音助手”“进入待机”立即打断并回到待机。默认 90 秒无新用户请求自动待机，无结束播报。否定句、引用和讨论控制命令不能触发操作。
- 待机不调用对话模型、不主动播报。设备原厂本地唤醒音、麦克风和屏幕亮起仍由厂家固件控制；没有对应接口时不能声称已禁用。
- 设备控制使用确定性中文命令匹配及同一连接的 MCP 工具。读取真实状态后执行相对音量调整，0～100 限幅；绝对音量越界时拒绝。静音保存本会话最近非零音量；无记录不猜测恢复值。
- 音量、亮度、状态、网络、电池、固件信息只使用设备实际公布的工具。只摘要白名单字段，网络密码不进入模型或日志。硬件文字反馈使用小智标准 TTS 文本消息；静音和待机反馈只发文字。
- 重启须先说“重启设备”，15 秒内再说“确认重启设备”；只有工具确实存在才执行。关机、配网没有实际工具时明确说明限制，不用重启冒充关机，不清空 Wi-Fi。
- 当前固件未确认支持断电关机、语音配网或关闭本地唤醒检测；断电后的语音开机依赖独立常供电电路，不由服务器实现。
- 启动入口只启动语音服务和 IoT，不默认启动网页。网页源码保留为独立调试工具。

## 实施计划

1. 在 `tests/test_device_control.py` 写指令误触发、待机门控、真实读回、静音恢复、工具缺失和重启确认测试，先验证失败。
2. 在 `src/device_control.py` 实现纯命令解析、会话开关及设备控制；通过注入调用函数隔离上游库。
3. 在 `src/hardware_control.py` 接入识别入口、异步 MCP 调用、设备能力记录、空闲待机与标准屏幕/语音反馈。接收循环不等待设备 RPC，避免死锁；关闭时取消旧任务，防止延迟工具结果重新触发回答。
4. 在 `scripts/run_server.py` 安装适配；关闭自动招呼和空闲结束语。调整 `scripts/start-assistant.ps1` 为硬件服务入口。
5. 回归测试与模拟设备 WebSocket 验证：默认不应答、语音启停、工具 RPC、错误反馈、重连恢复待机。模拟器只代表协议验收，不等于实体拾音和屏幕验收。
6. 停止网页、重启语音后台加载改动；等待实体设备连接并记录真实工具清单。无实体会话时如实保留验收缺项。

约束：保留上游子模块原样，不改板级引脚、不刷固件、不打开 COM5。密钥仍只保存在忽略的本地配置。根仓库没有提交身份，不为提交文档另造身份。
