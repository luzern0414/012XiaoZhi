# 小智本地语音助手开发方案

日期：2026-10-19（Asia/Shanghai）

## 目标与首阶段范围

在当前 Windows 工作目录中复用小智开源项目，建立可持续开发的本地服务端工程。先完成上游源码、项目约定、配置管理、启动入口和设备/网络诊断，再接通真实语音服务。首阶段不重刷固件、不修改设备 NVS、不改写现有 OTA 配置。

## 方案选择

1. **ESP32 + 本地 Python 服务端（采用）**：复用 `xinnan-tech/xiaozhi-esp32-server` 的 ASR → LLM → TTS 链路和 WebSocket 协议；自有扩展单独维护。硬件可继续使用已烧录的小智固件。
2. 沿用远程 OTA 服务：上手快，但无法直接管理远程服务端的对话逻辑、数据和模型配置。
3. 电脑端客户端：可用于无硬件开发，但不是本次已接入 ESP32 的主路线。

用户已选择方案 1。完整管理后台、Java/MySQL/Redis、固件重新编译均不作为第一阶段的必需依赖。

## 目录与依赖边界

| 路径 | 职责 |
| --- | --- |
| `firmware/xiaozhi-esp32/` | 官方 ESP32 固件独立 Git 仓库，保留上游许可证和历史来源 |
| `services/xiaozhi-esp32-server/` | Python 服务端及上游其他模块的独立 Git 仓库 |
| `src/` | 自有集成和业务扩展；避免不必要地修改上游 |
| `config/` | 可提交的配置模板；实际密钥放被 Git 忽略的本地配置 |
| `data/` | 私有设备信息、诊断报告、音频与模型缓存等运行数据 |
| `logs/` | 私有运行日志 |
| `scripts/` | Windows 开发环境准备、诊断、启动脚本 |
| `docs/` | 调研来源、架构、设备观察、开发与接入指南 |
| `tests/` | 后续自有代码的有效测试 |
| `tools/` | 本地工具及工具说明 |

自有诊断代码使用独立 Python 3.12 环境，避免当前系统 Python 3.14 的兼容性问题。上游服务端 requirements 已核实推荐 Python 3.10，锁定 torch 2.2.2 / numpy 1.26.4；服务端使用独立 Python 3.10 环境或官方 Docker 镜像。较重的本地识别模型按需要安装。

## 数据流

ESP32 通过 Wi-Fi 请求 OTA 接口获取 WebSocket 参数，再用 WebSocket 传输 Opus 音频。服务端完成语音活动检测、语音识别、模型对话、工具调用与语音合成。USB COM5 用于串口观察与未来固件开发，不替代 Wi-Fi 语音链路。

本机无线网卡观察地址为 `192.168.16.73`；配置设备时必须使用设备实际能访问的 LAN IP。现有远程 OTA `http://113.98.195.218:10802/xiaozhi/ota/` 保留为诊断参考。已核实上游 `app.py`、`config_loader.py` 与默认配置：WebSocket 8000，HTTP OTA 8003，自定义配置读取 `main/xiaozhi-server/data/.config.yaml`。

## 设备观察与处理约束

- Windows 已识别 Espressif USB 串口 COM5，VID 303A / PID 1001。
- 串口启动日志为 ESP32-S3、小智版本 2.0.3.3、ESP-IDF v5.5.1、16MB PSRAM。
- 打开串口导致 `USB_UART_CHIP_RESET`；诊断脚本默认只枚举设备，不自动打开串口。
- 固件报告 `/GetXConfig` 为无效 URL，须与厂家定制功能和配置核实，不能据此断言 OTA 失效。
- 远程 OTA GET 返回 HTTP 200、`OTA接口运行正常，websocket集群数量：1`；这仅证明接口存活，不证明设备已绑定或语音链路成功。

## 错误处理与验收

脚本遇到依赖缺失、配置缺失或端口占用时给出明确错误。密钥不写入模板与公开文档。验收分开记录：上游下载与提交号、目录和模板、环境准备、服务进程和协议握手、硬件真实对话。没有模型凭据或设备未切换到本地时，不宣称语音助手已完成端到端联调。

后续里程碑：先运行最小 Python 服务；再配置 ASR/LLM/TTS；再将 ESP32 接入本机并验证真实语音；最后按业务需要增加工具与记忆。
